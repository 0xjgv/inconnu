# Detector scoreboard

Minimize **cost** among candidates that pass all four gates. A leaked span has at least one gold character left visible. Each leaked secret costs 20, each leaked SSN, card or IBAN costs 10, and each leaked email, phone, person or IP costs 3. Each negative row with any redaction costs 1. The score is `100 × (1 − cost / cost of redacting nothing)`. A higher score is better within the same epoch.

Each epoch fixes the dev corpus by SHA-256. All rows in the section use that corpus, including the baseline. The row metadata also stores its corpus hash, exact per-kind counts, dependencies and measured revision. When new adversarial cases change the hash, score the previous passing detector on the new corpus first. Start a new section with that baseline and compare changes within that section. Use distinct negative category names for new cases. Different Python standard libraries or generator inputs can also change the hash.

¹ The four gates, in table order, are original-negative FRR at or below the epoch baseline, no kind losing more than one percentage point of full coverage against its parent row, paired latency within budget, and no additional declared runtime distribution. FRR is the fraction of negative rows with any redaction. Parent means the most recent recorded Git ancestor in the active epoch.

² Each latency entry shows the median candidate/baseline ratio and its [minimum–maximum] across five pairs, first for the 10k-cell batch, then for cell p99. Both detectors see identical cells and the same seeded batch order. The run order alternates by pair (AB, BA, AB, BA, AB). Each batch time is the median of five runs. The gate passes at batch ≤1.15× and p99 ≤1.25×. If either range is wider than its margin (0.15× or 0.25×), latency is UNSTABLE and the scorer exits 1 so the measurement can be retried. Otherwise an over-budget median fails. Use the same host and interpreter for both versions.

Run `make score` to see cost, score, all four gates, and exact leak counts by kind. A failed gate returns exit 1 from the scorer (`python -m evals.scoreboard score`). GNU Make reports a failed recipe as exit 2. Every detector PR appends a dev row using `make scoreboard LABEL="description"` after committing the detector. Supply `REASON="explanation"` for an increase in original FRR, a drop in aggregate secret full coverage, or a failed gate. A reason records the tradeoff and leaves the gate verdict intact. A recorded UNSTABLE attempt can be retried at the same revision. Both attempts stay visible. Commit the updated table in the PR.

Use `make scoreboard-holdout` as a sanity check. It prints a separate row for a fresh random seed of the same templates, with baseline and parent measured on that seed. Keep this sample out of optimization and keep the test split for release checks. These synthetic measurements do not establish production performance.
